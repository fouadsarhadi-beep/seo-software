# Workbench implementation checklist

**Status on 2026-11-28:** stages 1–6 are implemented with automated coverage; live Google checks remain pending owner credentials. Stage 7 has 7.1 and the shared/owned-only/competitor-only gap split done; the sample-compatibility warning, an add-to-brief action and question relationships (7.3–7.5) remain. Stage 7 expands its research follow-up. The first release target is stages 1–4: launch, crawl, investigate, share. The second is stages 5–7: explain performance, track decisions, explore opportunities.

## How to pick up the work

Take the first unchecked implementation item whose dependency is complete. Read its named entry points and their callers. Implement through the normal UI and reuse the operation behind the CLI. Mark an item complete in the same commit as the working change. In the [implementation log](IMPLEMENTATION_LOG.md), record stage, step, result and date. At the end of each stage, run its grouped checks and append the owner walkthrough to the [manual audit log](MANUAL_AUDIT_LOG.md). Mark Windows or live provider checks pending until an owner reports the result. Independent offline stages can proceed while those checks are pending.

Use the current FastAPI/Jinja UI, project-local workspace and run manifests. All proposed screens below can be server-rendered. Existing POST actions retain token validation, and downloads retain manifest-based access. Preserve direct run, evidence, archive, deletion and CLI entry points. A stage that introduces stored data must cover restart, old workspaces and deletion of the new data through the existing management flow.

## Why these screens

| Reference pattern | Implementation decision |
| --- | --- |
| Ahrefs Page Explorer offers presets that narrow a crawl to relevant URLs. | A summary count is a link to its exact table query. A user can add another filter, inspect evidence and return to the same rows. [Ahrefs Page Explorer](https://ahrefs.com/academy/how-to-use-ahrefs/site-audit/page-explorer) |
| Semrush leads from an issue to an explanation and a list of affected pages. | Each rule has an observation, reason to care, next check and evidence. Keep a finding count distinct from its affected URL count. [Semrush Issues](https://www.semrush.com/kb/541-site-audit-issues-report) |
| Semrush exports the data appropriate to the report being viewed. | Put Export matching pages by the table, and Full audit report on the overview. State the scope inside both files. [Semrush audit exports](https://www.semrush.com/kb/905-exporting-site-audit) |
| Ahrefs allows inspection of changes between two crawls down to a single URL. | Show both observations and their coverage. Partial crawls require an unassessed state. [Ahrefs crawl comparison](https://help.ahrefs.com/en/articles/5192078-how-to-compare-changes-between-two-crawls-in-site-audit) |
| Semrush Keyword Gap compares terms across domains. AlsoAsked shows relationships between questions. | Use compatible domain samples for overlap. Require observed parent–child relationships for question trees. Every result links to its source. [Semrush Keyword Gap](https://www.semrush.com/kb/28-keyword-gap) · [AlsoAsked](https://alsoasked.com/faqs) |

## Stage 3 — Explore an audit from a finding down to a page

Depends on 2.3. Today `GET /runs/{rid}` in `ui/server.py` filters findings and URL strings in memory and slices each into groups of 30. Different tools share that dispatcher. Isolate the audit branch before changing it. Keep checks and research result rendering covered.

- [x] **3.1 Define a read model against saved runs.** Inspect current and older manifests, stored evidence, inventory, findings and snapshot. Map requested URL, observed destination, HTTP status, indexability and reason, finding rule/category, evidence ID and run ID to their actual sources. Record one row per observed page; join findings through evidence IDs. One overlap finding with two evidence IDs yields one finding and two affected pages. Missing fields display Unknown. Keep stored URL identity, including encoded separators.
- [x] **3.2 Build one query for the page table.** Accept URL text, HTTP status/class, redirect, indexability, finding rule, sort and page. Combine filters with AND; validate allowed values. Match decoded display text as well as original URLs. Apply filters, count matches, stable-sort with a unique tie-breaker, then slice 30 rows. Return total observed, total matched and page bounds. Reuse this query for presets and filtered exports.
- [x] **3.3 Build Overview.** At the run URL show site, date, status and coverage first. Explain a 100-page cap once. Group findings by rule and category with separate occurrence and URL counts. Make page-level counters clickable only where the destination can reproduce the count. Put request totals and discovery diagnostics under run details.
- [x] **3.4 Build Findings and Pages.** Link Overview / Findings / Pages / Exports within the run. Rule detail opens with observed behavior, why it matters, next check and matching URLs. For noindex, ask whether exclusion was intended. On Pages show path, status, indexability and findings; link rows to existing evidence and show redirect destinations. When a row has missing evidence, explain the gap.
- [x] **3.5 Finish list navigation.** Persist tab, filters, sort and page in GET parameters. Preserve older bookmarked searches using `q`, `url_q`, `category`, `evidence_page` and `page`. At the bottom show range, matched count, previous/next and bounded page numbers. Reset page on filter change, clamp out-of-range pages and offer Clear filters on zero matches. Return from evidence to the same list using validated local state.
- [x] **3.6 Verify together.** On a fixture shaped like the owner's audit, “2 redirecting” opens exactly two observed source URLs. A pair finding resolves to both pages. Use the last page of an unfiltered 100-page run (rows 91–100), then filter and use Back. Check a one-page run, older run with unknown fields and failed run. Capture the baseline before editing the results route in 3.1, then time the same fixture after 3.5; if list rendering is slow, profile the reads before adding indexes.

## Stage 6 — Compare audits and follow up findings

Depends on stages 2–3; traffic context uses stage 5 when available. Reuse `/compare`, `ui/comparison.html`, `analysis/checks.py`, `analysis/review.py` and existing pair decisions.

- [x] **6.1 Choose comparable runs.** Start from a project/target, preselect the latest two compatible audits and let the user change either. Display dates, limits, observed counts and which checks ran before generating a comparison.
- [x] **6.2 Define changes using evidence.** Both crawls assessed a page/rule: show new, persistent or resolved as appropriate. Missing observation or unavailable check: show unassessed and the reason. A changed URL or redirect destination retains the recorded identities. Link each side to evidence from the correct date.
- [x] **6.3 Add a review queue.** Start from an issue or page; save status, note, project, rule, affected page identities and evidence reference. Reuse pair review for pairs. For other findings define a stable identity and evidence fingerprint. Repeated saves update the same decision; changed evidence reopens review while retaining the prior note. Scope queue records to their project and integrate with cleanup.
- [x] **6.4 Verify together.** Compare different caps, an observed fix, an unchanged issue and a changed pair. After restart verify the queue and note. With traffic data show its source/date beside priority; without data use observable severity and affected pages. Owner: follow one fix through two saved runs.

## Product acceptance across stages

Deliver these items alongside the named steps. They define what the operator must be able to accomplish in the finished local workbench. Both release walkthroughs below use the same project from one session to the next.

- [ ] **With 1.2 and 2.5 — First install and upgrade.** Try the README in a fresh Windows checkout with a supported Python installation and no virtual environment. List first-time setup separately from everyday double-click launch. A missing prerequisite should identify the exact next action. Then update a populated checkout, launch from a path containing spaces, and open a pre-update project, audit and download. Show the active data location in the UI.
- [ ] **With 2.3 — Design the actual screens.** Before editing the shared template, sketch the project overview, audit result and research source picker with the owner's examples. Use one prominent next action per screen. Keep project and target visible when a user leaves an overview. Check keyboard-only use, visible focus, status labels without color, 200% zoom and a Persian URL beside an English status label. Move secondary columns into page details if the table no longer fits.
- [x] **With 2.5 — Account for every existing tool.** Extend the route inventory with tool name, underlying operation, entry screen, prerequisites, example input and useful output. Include saved workflows, Site QA, Lighthouse and existing reporting tools. Exercise a local HTML build from the Site QA landing page and follow one observation to evidence. Label optional CLI-only utilities in the guide. A task advertised in navigation must lead to a working action or explain its prerequisite.
- [x] **With 3.1 — Specify what an audit actually checks.** Inventory rule IDs in `app/audit.py` and observation types in `analysis/checks.py`. For each rule family record whether it runs in the initial crawl or as a saved-snapshot check, evidence required, user-facing meaning and coverage limits. Surface available snapshot checks from the audit and link results back. For an internal link, distinguish a recorded 404, an unobserved destination and missing markup. Check these three cases in the UI at 3.6 and in exports at 4.5. Count a finding once if two views refer to the same observation.
- [ ] **With 3.6 — Recover interrupted work.** Close the tab during an active crawl, reopen the project and find progress or the finished run. Cancel an audit and retry it with its prior settings. Restart the server during another disposable run and reconcile any stale running status. Preserve earlier completed runs, identify partial artifacts, and prevent double submission from creating unintended duplicate jobs.
- [ ] **With 4.5 — Practice recovery and measure responsiveness.** Document the stopped-app backup and restore procedure in the README, including how to locate the active workspace and data directory. Follow it on a disposable workspace. Restore to a separate directory, open a project, evidence page and report, and confirm what requires credential reconnection. Separately measure Overview, filtered Pages and last-page navigation on the same saved 300-page fixture before and after the changes. Aim for each local response within one second on the recorded test machine; investigate misses and report actual timings. Record export time separately.
- [x] **With 5.5 — Publish capability status.** Update the verified/open table by provider and action: available offline, wired with fixture verification, verified live, or planned. Record date, environment and observed outcome. Distinguish authentication from successful retrieval and retrieval from publishing. Offline operation needs no account; the claim that a connected workflow works requires a successful owner run.
- [ ] **With 6.4 and 7.5 — Verify a return visit.** From a saved project reopen the same target and crawl settings, compare against the earlier audit and find the prior review note. Open a saved research result and recover the sources behind a selected question or keyword. Archive and remove a disposable run; subsequent visits should explain any unavailable source and keep unrelated projects usable.

## Release walkthrough

Run the existing CI suite at release checkpoints using the locked environment in `.github/workflows/test.yml`. Windows and Ubuntu cover installation and regression checks. The owner supplies the real browser, Excel, live site and consent checks. Record the commit, run IDs, fixture or live source, expected result and actual result in the manual log. Never substitute synthetic provider data for a live verification.

- [ ] **Release 1, after stage 4.** Double-click the launcher, choose the project, run a capped audit, open a grouped finding, filter pages, inspect one page and return, then share the offline report and reconstruct that finding from the bundle.
- [ ] **Release 2, after stage 7.** Import search and traffic data, trace a metric to its source, compare two audits, save a decision, select a competitor opportunity and turn a question branch into a brief. Record unresolved owner checks beside their stage.

- [ ] **Product sign-off.** Follow both walkthroughs using the README and visible UI alone on the owner's Windows machine. Reconcile one real site's counts with its export and record one actionable SEO decision with evidence. Record each failed task against its step, correct it and repeat that task. Summarize supported workflows, measured limits, known issues and pending provider checks in the implementation state document. Call the local release ready when the offline journeys pass and the owner can complete them unaided. Claim each live integration separately as its check passes.
